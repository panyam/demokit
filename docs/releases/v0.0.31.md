# v0.0.31

This release completes the markdown-native authoring path. A demo's content (notes, arrows, inputs, verbatim snippets) can now live entirely in a sidecar `demo.md`, behavior stays in Go, and a new `demokit` CLI scaffolds projects and migrates existing Go-defined walkthroughs. It is additive: every existing inline demo keeps working unchanged.

## Added

- **Verbatim blocks in sidecar markdown.** A fenced code block becomes a verbatim block with a `verbatim="<title>"` attribute; `label=` names a variant and `default=true` marks the preferred one. Consecutive same-title fences merge into one multi-variant block (the curl/go/python tabs), mapping to `VerbatimVariants`; a lone titled fence maps to `VerbatimLang`. Attributes are parsed by goldmark's own attribute parser. This closes the last content gap that kept verbatim-heavy demos tied to Go. (PR 72)
- **`harness` package.** `harness.Run(demo)` collapses the renderer/mode wiring every walkthrough used to copy by hand: it selects the renderer for `--mode` (plain/tui/notebook), enables `--doc bundle` / `--serve`, and runs the demo in one call. `harness.SetupRenderer(demo)` does the wiring without `Execute`. It is batteries-included (imports `tui` + `notebookbridge` + `web`); demos wanting a lean binary keep wiring renderers directly. (PR 73)
- **`harness.WireRecipe` / `harness.SplitLines`** authoring helpers, moved out of consumer projects that kept redefining them. (PR 73)
- **`--doc sidecar` renderer (`Demo.Sidecar()`).** Emits a demo's definition as sidecar markdown, the inverse of `FromMarkdown`. It walks the resolved demo model (never running steps), so `go run ./mydemo --doc sidecar > demo.md` lifts an inline demo's content into markdown, inputs and all. (PR 74)
- **`demokit` CLI** (`go install github.com/panyam/demokit/cmd/demokit@latest`):
  - `demokit init [dir]` scaffolds a project with a base Makefile and a runnable sample.
  - `demokit new <name> --kind=narrated|live|branching` adds an example from a starter (a per-example gradient; generated code imports only `demokit` + `harness`).
  - `demokit extract <file.go>` rewires a Go walkthrough's `Run`/`Coalesce`/`Timeout` closures into a `Bind(id)` skeleton, the one migration step that must read source. (PR 74)

## Changed

- **`FilterArgs` now strips demokit's complete flag set.** It previously omitted `--record`, `--replay`, `--out`, `--serve`, and `--input-timeout`, so consumers running their own `flag.Parse(FilterArgs(...))` had to hand-list them. A test now enumerates `RegisterFlags` and asserts each flag is stripped, so the two can't drift again. A caller's explicit `BoolFlag("--serve")` still wins, so existing usage is unaffected. (PR 73)
- `examples/graph` and `examples/dungeon` now use `harness.Run`, which also gives their TUI/notebook output the copy-friendly `BorderHorizontalOnly` style. `examples/basic` and `examples/verbatims` keep manual wiring on purpose, as the custom-path examples. (PR 73)

## Migrating an existing Go demo to sidecar

```bash
go run ./mydemo --doc sidecar > demo.md       # content, from the demo model
demokit extract mydemo.go --out bindings.go   # behavior, from source
```

The content path handles everything the demo declares because it reads the built model; `extract` only carries the `Run` closures, which can't be reconstructed from a function value. It warns when a bound step lacks an explicit `.ID()`, the join key the markdown and the binding must share.
